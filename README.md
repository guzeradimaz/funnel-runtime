# Funnel Runtime

Мини-платформа для многошаговых веб-воронок. Экраны приходят с сервера как JSON-конфиг. Есть версии с публикацией и откатом, A/B-эксперимент внутри версии, собственный приём событий и аналитика по уникальным сессиям.

**Публичный URL: https://funnel.guzerchuk.site** — воронка, [/admin](https://funnel.guzerchuk.site/admin), [/dashboard](https://funnel.guzerchuk.site/dashboard). Внутренние страницы на демо-стенде открыты без токена, чтобы проверяющим было удобно.

Текст задания лежит в [TASK.md](TASK.md). Репозиторий: https://github.com/guzeradimaz/funnel-runtime

| Страница | Путь |
|---|---|
| Воронка | `/` (QA: `/?variant=A`, `/?variant=B`, UTM: `?utm_source=…&utm_campaign=…`) |
| Версии: публикация, откат, загрузка конфига | `/admin` |
| Аналитика | `/dashboard` |

## Запуск локально

Нужен Node.js 22.12 или новее: этого требуют `better-sqlite3`, `vitest` и `vite`. Других сервисов нет: база — файл SQLite `data/funnel.db`.

```bash
npm install
npm run dev          # API на :3000 и Vite на :5173 → http://localhost:5173
```

Production-режим, один процесс:

```bash
npm run build && npm start   # http://localhost:3000
```

При первом старте сервер загружает `configs/*.json` (v1 и v2) в хранилище версий и публикует v1. Конфиг второй итерации лежит отдельно: `configs/iteration-2/funnel-v3.json`. Его загружают через `/admin` или скриптом `npm run demo`, без передеплоя.

### Тестовый трафик

Сервер должен быть запущен.

```bash
npm run traffic -- --sessions 150 --seed 42   # 150 синтетических сессий на активной версии
npm run demo                                  # обе итерации целиком, см. ниже
```

Генератор работает через настоящий HTTP API, как браузер. Он создаёт сессии с разными UTM, получает варианты A и B от сервера (5% через override) и проходит разные ветки. Сессии отваливаются на разных шагах, иногда возвращаются назад и повторно смотрят шаг. Генератор также портит доставку событий:

- переставляет пачки местами (события приходят не по порядку);
- повторяет пачку целиком (ретрай после таймаута);
- дублирует событие внутри пачки;
- подмешивает битое событие в нормальную пачку.

После прогона генератор сравнивает свой ground truth (сколько сессий начато, дошло до результата и кликнуло CTA) с приростом цифр на дашборде. Если не совпало, он завершается с кодом 1:

```
Generated 120 sessions (4 with QA override, excluded from analytics): 591 batch requests, 2575 accepted, 322 duplicates ignored, 20 malformed rejected
  v2 A: started 72, result 42, cta 22 | dashboard delta 72/42/22 OK
  v2 B: started 44, result 21, cta 13 | dashboard delta 44/21/13 OK
```

## Публичный URL

Развёрнуто на https://funnel.guzerchuk.site (VPS, Ubuntu 24.04):
- системный пользователь `funnel`, код в `/opt/funnel-runtime/app` (клон этого репозитория), база в `/opt/funnel-runtime/data`;
- systemd-сервис `funnel-runtime` (`HOST=127.0.0.1`, `PORT=3420`, автоперезапуск);
- nginx как reverse proxy, сертификат Let's Encrypt через certbot, редирект с http на https;
- `ADMIN_TOKEN` не задан: на демо-стенде `/admin` и `/dashboard` открыты всем. Это сознательное допущение для проверки задания. Любой посетитель может публиковать и откатывать версии; для боевого использования токен нужно вернуть в `/etc/funnel-runtime.env`.

На этом стенде прогнаны `npm run demo` (обе итерации, публикация и откат), `npm run traffic` и браузерные сценарии. Обновление: `git pull && npm ci && npm run build` в `/opt/funnel-runtime/app` от пользователя `funnel`, затем `systemctl restart funnel-runtime`.

Другие варианты запуска. Сервис — один контейнер без внешних зависимостей. Состояние хранится в SQLite на диске.

- **Render:** `render.yaml` в корне. Нужен Blueprint из репозитория; он создаёт web service и диск под `/app/data`, `ADMIN_TOKEN` генерируется автоматически.
- **Любой Docker-хост:** `docker build -t funnel . && docker run -p 3000:3000 -v funnel-data:/app/data -e ADMIN_TOKEN=secret funnel`. Образ локально не собирался (на машине разработки не было Docker); `npm ci && npm run build && npm start` проверены на чистом клоне.
- **Временный URL с локальной машины:** `cloudflared tunnel --url http://localhost:3000`.

Если задан `ADMIN_TOKEN`, его требует API `/api/admin/*`: заголовок `x-admin-token` или параметр `?token=`. Страницы `/admin` и `/dashboard` загружаются без токена, но без него не получат данные: они сами спросят токен и сохранят его в браузере. Скрипты берут токен из переменной окружения `ADMIN_TOKEN`.

В `render.yaml` указан тариф `starter`: постоянный диск под SQLite на бесплатном тарифе Render недоступен. На бесплатном тарифе сервис тоже запустится, но база будет сбрасываться при каждом перезапуске.

## Архитектура

```
configs/                    JSON-конфиги воронки (v1, v2; v3 — в iteration-2/)
src/shared/                 общий код клиента, сервера, генератора и тестов
  engine.ts                 условия, видимость шагов, следующий шаг, прогресс, результат, валидация
  validateConfig.ts         структурная проверка конфига перед сохранением
src/server/
  db.ts                     SQLite и версионированные миграции
  versions.ts               хранилище версий, публикация, откат
  sessions.ts               сессии, закрепление версии, назначение варианта, состояние
  events.ts                 приём пачек событий
  analytics.ts              агрегаты для дашборда
  app.ts                    HTTP-роуты
src/web/                    React: воронка, /admin, /dashboard
scripts/                    генератор трафика и демо обеих итераций
tests/                      vitest
```

Движок воронки — чистые функции в `src/shared`. Браузер, сервер, генератор и тесты считают ветвления, прогресс и результат одним и тем же кодом. Поэтому генератор проходит воронку так же, как пользователь.

### Как работает воронка

- Конфиг описывает все шаги. Вариант эксперимента задаёт порядок шагов (`stepSequence`) и переопределения текстов и результатов. Сервер склеивает конфиг для варианта сессии (`resolveFunnel`) и отдаёт клиенту только его.
- Типы шагов: `info`, `single-select`, `multi-select`, `number`, `result`. Ветвление задаёт `visibleWhen` с операторами `eq`, `neq`, `in`, `not_in`, `contains`, `gt`, `gte`, `lt`, `lte`, `exists` и комбинаторами `all`, `any`, `not`.
- Следующий шаг — ближайший видимый шаг после текущего. Видимость считается по ответам на видимые шаги (`effectiveAnswers`). Если пользователь вернулся и сменил ответ так, что ветка закрылась, старые ответы этой ветки не влияют ни на результат, ни на прогресс.
- Прогресс считает только видимые шаги без `info` и `result`. Когда ветка открывается, растёт знаменатель: в варианте A v2 при ответе «Fully remote» на втором вопросе следующий шаг показан как «3 / 7», а при ответе «Hybrid» как «3 / 8»: открылся шаг `office_days`.
- Состояние — это ответы и стек пройденных шагов. Оно хранится на сервере в сессии и дублируется в `localStorage` с номером ревизии `rev`. После refresh или повторного открытия берётся более свежая копия. Сервер игнорирует запись со старым `rev`, например запоздавший запрос из другой вкладки.
- Сервер не доверяет присланному состоянию (`normalizeState`). Ответ сохраняется, только если проходит валидацию шага. История принимается, только если это настоящий путь: каждый следующий шаг равен `nextStepId` от предыдущего. Подделать прохождение («intro → result») нельзя.
- Кнопка Back в интерфейсе и кнопка «назад» браузера идут через один обработчик `popstate`. На каждый шаг есть запись в истории браузера; после восстановления сессии записи создаются заново.
- `session_id` хранится в `localStorage`. Если сессия истекла (TTL 72 ч из конфига) или не найдена, создаётся новая.

## Модель данных

SQLite, миграции в `src/server/db.ts`. Список миграций только дополняется; применённые фиксируются в `schema_migrations`.

| Таблица | Назначение |
|---|---|
| `funnel_versions (funnel_id, version)` | Неизменяемые конфиги: JSON, checksum, release note. Повторная загрузка того же конфига ничего не делает. Тот же номер с другим содержимым — 409. |
| `funnel_active (funnel_id)` | Указатель на версию, на которой стартуют новые сессии. |
| `publications` | Журнал публикаций и откатов (`version`, `from_version`, `action`). По нему считается цель отката. |
| `sessions` | `id`, закреплённые `version`, `experiment_id`, `variant`, `variant_source` (`hash` или `override`), UTM, `state_json`, `expires_at`. |
| `events` | Одна строка — одно событие. `event_id` — первичный ключ и ключ идемпотентности. |

### Версии и откаты

- **Публикация** (`POST /api/admin/funnels/:id/publish`) переключает `funnel_active` и пишет строку в журнал. Перезапуск не нужен: конфиг читается из БД при создании сессии.
- **Откат** (`POST /api/admin/funnels/:id/rollback`) возвращает версию, из которой была опубликована текущая. Берётся последняя строка `publish` для активной версии. Строки `rollback` не считаются целью отката, поэтому откат после цепочки v1→v2→v3 даёт v3→v2→v1, а не прыжки туда-обратно.
- **Закрепление.** Сессия хранит свою версию и вариант. `GET /api/sessions/:id` всегда отдаёт конфиг закреплённой версии. Начатые сессии доигрывают на старой версии после публикации или отката, новые стартуют на активной.
- **Загрузка** (`POST /api/admin/versions`, `?publish=1` — сразу опубликовать). Сервер проверяет конфиг:
  - каждый шаг из `stepSequence` существует;
  - в каждом варианте не меньше 6 шагов, последний — `result`;
  - условие ссылается только на ответы, которые задаются раньше в этом варианте;
  - правила результата ссылаются на существующие результаты;
  - в конфиге есть хотя бы одна ветка и все обязательные события.

## Event schema

`POST /api/events` с телом `{ "events": [ … ] }`. Можно передать просто массив. Принимается `application/json` и `text/plain` (`sendBeacon`), до 200 событий в пачке.

```jsonc
{
  "event_id": "1b9d…",              // UUID с клиента; ключ идемпотентности
  "session_id": "…",
  "name": "step_completed",
  "step_id": "work_mode",
  "client_ts": "2026-10-05T12:00:00.000Z",
  "properties": { "next_step_id": "priorities" },
  // клиент также шлёт funnel_version, variant, utm_* — сервер их игнорирует, см. ниже
}
```

Что хранится в каждой строке `events`: `event_id`, `session_id`, `name`, `funnel_id`, `funnel_version`, `experiment_id`, `variant`, `step_id`, `utm_source`, `utm_medium`, `utm_campaign`, `client_ts`, `server_ts`, `properties_json`.

| Событие | Когда | Свойства |
|---|---|---|
| `session_started` | Сервер создал сессию. Пишется самим сервером в той же транзакции; `event_id = session_started:<session_id>`. | — |
| `step_viewed` | Шаг показан, в том числе повторно после refresh или возврата. | `step_type`, `visible_step_index`, `visible_step_count` |
| `answer_submitted` | Валидный ответ отправлен. | `answer_kind` (`single`, `multi:<count>`, `number`), без значения ответа |
| `step_completed` | Переход вперёд. Пишется и для `info`-шагов, чтобы intro имел свою конверсию. | `next_step_id` |
| `back_clicked` | Возврат назад (кнопкой или браузером). | `destination_step_id` |
| `result_viewed` | Показан результат. | `result_id` |
| `cta_clicked` | Нажат основной CTA. | `result_id`, `action` |
| `recommendation_expanded` | **Только v3.** Детальные рекомендации раскрылись после CTA. Сейчас CTA сразу раскрывает рекомендации, поэтому событие идёт парой с `cta_clicked`. Оно отделяет «намерение» (клик) от «доставки ценности» (контент показан): если раскрытие станет асинхронным или платным, события разойдутся. | `result_id`, `action`, `source` |

Правила приёма:

- **Идемпотентность.** `INSERT OR IGNORE` по `event_id`. Повтор пачки после таймаута или дубль внутри пачки получают статус `duplicate` и не пишутся второй раз. Клиент присваивает `event_id` при создании события и при ретрае шлёт тот же id.
- **Независимость событий в пачке.** Каждое событие валидируется отдельно. Ответ содержит статус по каждому: `{accepted, duplicate, rejected, results: [{event_id, status, error?}]}`. Битое событие получает `rejected` и не мешает остальным.
- **Контракт по закреплённой версии.** Допустимые имена событий, `step_id` и свойства берутся из конфига версии этой сессии. `recommendation_expanded` принимается для сессий v3 и отклоняется для v1 и v2. Новое событие не требует изменения схемы БД.
- **Источник версии, варианта и UTM — сессия.** Значения клиента игнорируются, поэтому в каждом событии они гарантированно верные.
- **Приватность.** В `properties_json` попадают только свойства, объявленные для события в конфиге, и только скалярные значения. Сырой ответ, присланный клиентом, отбрасывается. Ответы есть только в `sessions.state_json`: без них нельзя восстановить воронку после refresh. В аналитику они не попадают.

Клиентская очередь событий (`src/web/tracker.ts`) хранится в `localStorage`. Пачки уходят каждые ~400 мс с таймаутом 5 с. При ошибке сети очередь повторяется с экспоненциальной паузой. Когда страница скрывается, остаток очереди уходит через `sendBeacon`. События остаются в очереди и при следующем открытии отправляются ещё раз — сервер их отбросит как дубли.

## Правила агрегации

Код: `src/server/analytics.ts`.

1. **Все метрики считаются по уникальным сессиям.** Дубли отсекаются ещё при приёме, а внутри сессии события сворачиваются в множества: какие шаги показаны, какие завершены, был ли результат и CTA.
2. **Порядок событий и время не используются.** Прогресс сессии — множество достигнутых шагов. Поэтому события не по порядку, повторные просмотры и возвраты назад не меняют цифры.
3. **Более позднее событие подразумевает раннее.** `step_completed` и `answer_submitted` означают, что шаг был показан; `cta_clicked` означает, что результат был показан. Если одно событие потерялось, доли не превысят 100%.
4. **Отвал** засчитывается сессии без результата на её самом дальнем шаге. «Самый дальний» — по позиции в последовательности шагов её версии и варианта, а не по последнему пришедшему событию. Пример: пользователь дошёл до шага 5, вернулся на 3 и ушёл — отвал на шаге 5.
5. **Сверка.** Для каждого варианта `начали = без просмотра шага + Σ отвалов + дошли до результата`. Дашборд показывает это равенство под таблицей шагов.

| Метрика | Формула |
|---|---|
| Начали | сессии с `session_started` |
| Видели шаг | сессии, где шаг показан (с учётом правила 3); доля — от начавших |
| Конверсия между шагами | перешли со шага дальше (`step_completed`) / видели шаг. Для шага перед веткой показана разбивка по следующему шагу: «→ office_days 48%, → async_maturity 52%» |
| Отвал на шаге | правило 4; доля — от видевших шаг |
| Дошли до результата | сессии с результатом / начавшие |
| CTR CTA | сессии с CTA / сессии с результатом |
| **CTA / начавшие** | сессии с CTA / начавшие — основная метрика эксперимента |

QA-сессии с принудительным вариантом (`variant_source = override`) не рандомизированы, поэтому по умолчанию в аналитику не входят: они исказили бы A/B. Дашборд показывает, сколько таких сессий исключено, и их можно включить переключателем «QA-сессии». Это важно при ручной проверке: сессия, открытая по ссылке `/?variant=A`, без переключателя на дашборде не видна. Счётчики событий, повторных просмотров и QA-сессий учитывают фильтр версии.

Фильтры: версия и `utm_campaign` (включая `(none)` — трафик без UTM). Пошаговая воронка строится для одной версии, потому что у версий разный набор шагов. Сравнение версий и вариантов показано отдельной таблицей. Для A/B считается двусторонний z-тест двух долей.

## A/B-эксперимент

**Назначение.** Сервер считает `sha256(experiment_id:session_id)` и раскладывает результат по весам вариантов. Назначение детерминировано и сохраняется в сессии, поэтому после refresh вариант не меняется. Override для QA: `?variant=B` (имя параметра берётся из `experiment.overrideQueryParam` конфига). Неизвестное значение игнорируется. Override применяется только при создании сессии и помечается `variant_source = override`. Если override расходится с вариантом уже открытой сессии, создаётся новая сессия: менять вариант живой сессии нельзя.

**Гипотеза.** Вариант B снимает трение в начале и сильнее мотивирует на результате. Это одна гипотеза во всех версиях; меняются только формулировки:

- B начинает с понятного вопроса о формате работы (`work_mode`), а не с числового ввода размера команды. В v2 и v3 сразу за ним идёт вопрос о встречах, а в v3 из B убран вопрос `tool_count` — воронка короче;
- intro B сформулирован как проблема: «How should your team really work?» (v1), «Is your team losing time to the way it works?» (v2, v3);
- заголовки результата в B звучат как персональный диагноз, а CTA обещает конкретику: «See the 30-day action list» (v1), «Reveal the first three changes» (v2), «Open the implementation details» (v3). В A у CTA нейтральная подпись «View the action list».

Ожидание: в B больше сессий доходят до результата, и выше CTR CTA.

У каждой версии свой `experiment.id` (`…-v1`, `…-v2`, `…-v3`): после смены версии меняется сама воронка, и результаты разных версий нельзя складывать в один тест. Поэтому A/B на дашборде считается внутри выбранной версии.

**Основная метрика:** доля начавших сессий, нажавших основной CTA (`cta_clicked / session_started`). Она учитывает и прохождение воронки, и интерес к рекомендации, поэтому «короче, но хуже» не выиграет.

**Guardrails:** доля дошедших до результата, отвал на первом вопросе, распределение типов результата. Перестановка шагов не должна сдвигать рекомендации.

**Решение:** z-тест двух долей, α = 0.05. При базовой конверсии около 25% и ожидаемом эффекте +7 п.п. нужно примерно 670 сессий на вариант (мощность 80%). Синтетический трафик генератора меньше и с заложенным эффектом. Он проверяет механику, а не саму гипотезу.

## Вторая итерация (v3)

Что меняет `configs/iteration-2/funnel-v3.json`:

- **Условная ветка.** Добавлен шаг `security_constraints`. Он показывается, если в `priorities` выбрано `compliance`. Добавлен результат `regulated_scale`.
- **Удалён экран для варианта B.** В B больше нет `tool_count`.
- **Новое событие.** `recommendation_expanded`.

Что для этого понадобилось:

- В коде нет ничего специфичного для v3, схема БД не менялась (миграция одна). Честная оговорка: v3 был известен заранее, и движок с самого начала проектировался так, чтобы покрыть его — оператор `contains`, события как имя и JSON свойств, контракт событий по закреплённой версии. Клиент шлёт `recommendation_expanded`, только если событие есть в `allowedEvents` закреплённой версии.
- Старые сессии v2, начатые до публикации v3, получают свой конфиг v2 и доигрывают без ошибок. Это проверяет и тест, и демо-сценарий.

`npm run demo` проходит обе итерации через HTTP:

1. Трафик на v1. Пять сессий брошены посередине.
2. Публикация v2. Новые сессии идут на v2. Брошенные сессии v1 доигрывают на v1.
3. Трафик на v2.
4. Загрузка v3 через API и публикация. Брошенные сессии v2 доигрывают на v2. Трафик на v3.
5. Откат v3 → v2. Новые сессии идут на v2. Сессии v3 доигрывают на v3.
6. Проверка, что аналитика всех версий на месте.

На каждом этапе цифры дашборда сверяются с ожидаемыми: для трафика — с ground truth генератора, для доигранных старых сессий — что каждая добавила ровно один результат своей версии и не добавила новых начавших. Любое расхождение даёт `Demo FAILED` и код выхода 1.

## Допущения и ограничения

- **Одна воронка в демо** (`workstyle-planner`). Модель данных поддерживает несколько воронок.
- **Аналитика считается на лету** в Node по таблице `events`. Для тестового объёма это миллисекунды. На миллионах событий нужны предагрегаты по `(version, variant, campaign, step)` или материализованная таблица сессий.
- **Отвал шага** определён по самому дальнему шагу. Конверсия между шагами считается как «видели шаг → перешли дальше», а не как отношение соседних строк таблицы: у условных шагов следующий шаг разный, и отношение соседних строк вводило бы в заблуждение.
- **Поля `loadingTitle`, `errorTitle`, `retryLabel`** шага `result` не используются: результат считается на клиенте синхронно, состояний загрузки и ошибки у него нет. `progress.countVisibleOnly` считается всегда включённым.
- **Ответы в `sessions.state_json`** нужны для восстановления. Сейчас они хранятся бессрочно; в продакшене их стоит чистить после `expires_at`.
- **Очередь событий в `localStorage` общая для вкладок.** Если две вкладки открыты одновременно и одна закрылась до отправки, её неотправленные события может перезаписать другая вкладка. Для воронки это редкий сценарий. Исправляется очередью с ключом по сессии.
- **Admin-доступ** — один общий токен. Ролей и аудита по пользователям нет.
- **Результат считается на клиенте** общим движком. Сервер его не перепроверяет, поскольку для воронки-рекомендации это не критично.
- **Нет интеграционного входа** для старта воронки в iframe или под другим доменом: сессия привязана к `localStorage` одного origin.
- **Визуального редактора конфигов нет**, по условию задания. Новая версия загружается JSON-файлом через `/admin` или API.
